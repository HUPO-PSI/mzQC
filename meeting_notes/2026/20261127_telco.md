## mzQC Manuscript Revision

* The manuscript received a minor revision with generally positive reviews. The group aims to resubmit early next week; a fast turnaround may allow a decision before the end of the year.
* Both reviewers asked questions that confuse the format with the metrics, a long-standing misconception. The manuscript already makes the distinction, so the response restates it briefly without becoming redundant.
* File sizes: mzQC files range from a few kilobytes to a few megabytes, and repository-scale files are a few gigabytes that compress well. Chris showed that the full 4.3 GB repository-scale file can be loaded into a relational database with sub-second queries. This is useful for dashboards and future storage infrastructure, but it will not be added to the manuscript because it goes beyond the reviewer's question.
* Ion mobility: no specific metrics exist yet, but they can be added to the CV. The response will note that the upcoming mzML revision will support ion mobility isolation windows for DIA, and that wider visibility of mzQC may encourage developers to export ion mobility metrics.
* Repository deposition: the group strongly encourages depositing mzQC files with raw data and sees metric-based dataset discovery as future work.
* Stefan provided the clarification of major and minor interventions in the GC–MS use case. The response will also emphasize that this dataset was newly deposited together with its mzQC files.
* Questions about specific metrics (oxidized peptides, chromatography beyond FWHM, spatial techniques such as Deep Visual Proteomics) are answered as possible with mzQC, following a demand-driven approach to defining CV terms.
* Recommended core metric sets per modality and sample type: the group will not commit to a best-practices document now. One or two sentences on future work will be added to the conclusion, linked to repository-scale QC and metric categorization.
* Viewing mzQC files: mzQC decouples producing tools from consuming tools. The conclusion now mentions software independence and the new mzQC viewer.
* Consuming mzQC created by another party: existing use cases already demonstrate this. The response will point to the text added about separating metric generation from interpretation, note that the earlier mzQC paper focused on reading libraries, and give a reuser example, such as selecting the best-performing files from a large ProteomeXchange dataset.
* Documentation: supported tools, libraries, and CV terms remain online documentation rather than supplementary material so they stay up to date.

* Mathias presented a new mzQC viewer inspired by markdown editors. It provides generic structured rendering, automatic XY plots, and specialized rendering for imaging data, including 1–99% percentile scaling to handle outlier pixels.
